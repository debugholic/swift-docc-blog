# 1. 단위 테스트의 목표

## 요약

단위 테스트가 무엇을 위해 존재하는지, 그리고 커버리지 지표로 테스트 스위트의 품질을 재려는 시도가 왜 실패하는지 알아봅니다.

### 1.1 단위 테스트의 현재 상태

* 지난 20년간 단위 테스트는 대부분의 회사에서 사실상 필수가 되었습니다.
* 이제 논쟁은 **'단위 테스트를 작성해야 하는가'** 가 아니라 **'좋은 단위 테스트란 무엇인가'** 로 옮겨갔습니다.
* 혼란은 바로 이 지점에 남아 있습니다.
  - 자동화된 테스트가 많은 프로젝트인데도 기대한 효과가 나오지 않습니다.
  - 새 기능은 하염없이 늦어지고, 이미 검수된 기능에서 버그가 계속 나옵니다.
  - 도움이 되어야 할 테스트가 상황을 오히려 악화시키기도 합니다.
* 좋은 테스트와 나쁜 테스트의 차이는 취향의 문제가 아니라 프로젝트의 성패가 걸린 문제입니다.

> 엔터프라이즈 애플리케이션이란 조직의 내부 프로세스를 자동화하거나 보조하는 애플리케이션입니다.
>
> 높은 비즈니스 로직 복잡도, 긴 수명, 중간 정도의 데이터 양, 낮거나 중간 수준의 성능 요구사항을 특징으로 합니다.

### 1.2 단위 테스트의 목표

* 단위 테스트를 하면 설계가 좋아진다는 말은 사실입니다. 그러나 그것은 **주된 목표가 아니라 유쾌한 부수 효과** 입니다.

> 정의: 단위 테스트의 목표는 소프트웨어 프로젝트의 **지속 가능한 성장(sustainable growth)** 을 가능하게 하는 것입니다.

* **지속 가능** 이라는 말이 핵심입니다.
  - 프로젝트를 성장시키는 것 자체는 쉽습니다. 특히 처음부터 시작할 때는 그렇습니다.
  - 어려운 것은 그 성장을 오랫동안 **유지** 하는 일입니다.

* 테스트가 없는 프로젝트의 성장 곡선
  - 초반에는 빠릅니다. 발목을 잡을 것이 없기 때문입니다.
  - 시간이 지날수록 같은 진척을 내는 데 점점 더 많은 시간이 듭니다.
  - 결국 개발 속도가 현저히 떨어지고, 심하면 아무 진전도 못 내는 지점에 이릅니다.

* 이 현상을 **소프트웨어 엔트로피(software entropy)** 라고 부릅니다.
  - 엔트로피는 시스템의 무질서도를 뜻하며, 소프트웨어에도 똑같이 적용됩니다.
  - 코드를 수정할 때마다 무질서도가 조금씩 올라가고, 정리하지 않으면 도미노처럼 번집니다.
  - 결국 코드베이스를 신뢰할 수 없게 되고, 안정 상태로 되돌리기가 매우 어려워집니다.

* 테스트는 이 경향을 뒤집는 **안전망** 입니다.

> 정의: **회귀(regression)** 란 어떤 사건(대개 코드 수정) 이후 기능이 의도한 대로 동작하지 않게 되는 것입니다.
>
> 회귀와 소프트웨어 버그는 같은 말로 쓸 수 있습니다.

* 물론 테스트를 작성하는 데에는 초기 비용이 듭니다.
* 그러나 프로젝트 후반의 성장을 돕는 것으로 그 비용을 회수합니다.
* 코드베이스를 지속적으로 검증해 주는 테스트 없이는 개발이 **확장되지 않습니다.**

##### 1.2.1 좋은 테스트와 나쁜 테스트를 가르는 것

* 테스트를 쓰기만 해서는 부족합니다. 잘못 쓴 테스트는 같은 결말로 이어집니다.
* 나쁜 테스트도 초반에는 코드 부패를 늦춰 줍니다.
  - 테스트가 전혀 없을 때보다는 개발 속도 하락이 완만합니다.
  - 그러나 큰 그림은 달라지지 않습니다. 침체 단계에 들어가는 시점이 늦춰질 뿐, 침체 자체는 피할 수 없습니다.

* **모든 테스트가 동등하지 않습니다.**
  - 어떤 테스트는 소프트웨어 품질에 크게 기여합니다.
  - 어떤 테스트는 거짓 경보만 울리고, 회귀를 잡아내지도 못하며, 느리고 유지하기 어렵습니다.

* 프로젝트에 테스트를 더 많이 던져 넣는 것으로는 목표를 달성할 수 없습니다.
* 테스트의 **가치** 와 **유지 비용** 을 함께 따져야 합니다.
* 유지 비용은 다음 활동에 드는 시간으로 결정됩니다.
  - 대상 코드를 리팩토링할 때 테스트를 함께 고치는 시간
  - 코드가 바뀔 때마다 테스트를 실행하는 시간
  - 테스트가 울린 거짓 경보를 처리하는 시간
  - 대상 코드의 동작을 이해하려고 테스트를 읽는 시간

> 코드는 자산이 아니라 **부채(liability)** 입니다.
>
> 코드를 늘릴수록 잠재적 버그의 표면적이 넓어지고 유지 비용이 올라갑니다.
>
> 테스트도 코드이며, 다른 코드와 마찬가지로 버그에 취약하고 유지보수를 필요로 합니다.

* 따라서 유지 비용이 높아 순가치가 0이거나 음수인 테스트가 쉽게 만들어집니다.
* 지속 가능한 성장을 위해서는 **고품질 테스트에만** 집중해야 하며, 그런 테스트만 스위트에 남길 가치가 있습니다.

> 코드를 단위 테스트할 수 있는가는 **좋은 부정 지표** 입니다.
>
> 테스트하기 어렵다면 코드에 문제가 있다는 강한 신호입니다. 보통 강결합의 형태로 드러납니다.
>
> 그러나 반대 방향으로는 성립하지 않습니다. 테스트하기 쉽다고 해서 좋은 코드라는 보장은 없습니다.

### 1.3 커버리지 지표로 테스트 스위트 품질 측정하기

> 정의: **커버리지 지표(coverage metric)** 는 테스트 스위트가 소스 코드를 얼마나 실행하는지를 0%에서 100%로 나타냅니다.

* 흔한 믿음은 커버리지 수치가 높을수록 좋다는 것입니다.
* 그러나 커버리지 지표는 유용한 피드백을 주기는 해도 테스트 스위트의 품질을 측정하지는 못합니다.
* 단위 테스트 용이성과 마찬가지로, 커버리지 역시 **좋은 부정 지표이지만 나쁜 긍정 지표** 입니다.

##### 1.3.1 코드 커버리지 지표

> 정의: 코드 커버리지(테스트 커버리지) = 테스트가 실행한 코드 라인 수 ÷ 전체 코드 라인 수

```swift
func isStringLong(_ input: String) -> Bool {
  if input.count > 5 {
    return true
  }
  return false
}

func test_isStringLong() {
  let result = isStringLong("abc")
  XCTAssertFalse(result)
}
```

* 메서드 전체 라인 수는 중괄호를 포함해 5줄입니다.
* 테스트는 `return true` 를 제외한 4줄을 실행하므로 커버리지는 4/5 = **80%** 입니다.

이제 불필요한 `if` 문을 인라인해 보겠습니다.

```swift
func isStringLong(_ input: String) -> Bool {
  return input.count > 5
}
```

* 테스트가 세 줄을 모두 실행하므로 커버리지는 **100%** 로 올라갑니다.
* 그런데 테스트 스위트가 나아졌을까요? 그렇지 않습니다.
  - 메서드 안에서 코드를 옮겼을 뿐이고, 테스트가 검증하는 결과의 수는 그대로입니다.
* 즉, **코드를 압축할수록 커버리지 수치는 좋아집니다.** 지표가 순수한 라인 수만 세기 때문입니다.

##### 1.3.2 분기 커버리지 지표

> 정의: 분기 커버리지 = 테스트가 통과한 분기 수 ÷ 전체 분기 수

* 라인 수 대신 `if`, `switch` 같은 **제어 구조** 에 초점을 맞추므로 코드 커버리지보다 정밀합니다.
* 위 예시의 `isStringLong` 에는 분기가 두 개(길이가 5 초과인 경우와 아닌 경우) 있고, 테스트는 하나만 통과하므로 분기 커버리지는 1/2 = **50%** 입니다.
* 코드를 어떻게 표현하든 분기 수는 달라지지 않으므로, 앞서 본 방식으로 지표를 조작할 수 없습니다.

##### 1.3.3 커버리지 지표의 문제점

분기 커버리지가 더 낫기는 해도, 두 지표 모두 품질 판단에 쓸 수 없습니다. 이유는 두 가지입니다.

* **테스트가 모든 결과를 검증한다고 보장할 수 없습니다.**

```swift
private(set) var wasLastStringLong = false

func isStringLong(_ input: String) -> Bool {
  let result = input.count > 5
  wasLastStringLong = result     // 두 번째 결과
  return result                  // 첫 번째 결과
}

func test_isStringLong() {
  let result = isStringLong("abc")
  XCTAssertFalse(result)         // 첫 번째 결과만 검증한다
}
```

  - 이제 메서드에는 반환값이라는 명시적 결과와 프로퍼티 변경이라는 암묵적 결과, 두 가지가 있습니다.
  - 두 번째 결과를 검증하지 않았는데도 커버리지 수치는 그대로입니다.
  - 커버리지는 코드가 **테스트되었다** 는 사실이 아니라 **실행되었다** 는 사실만 보여줍니다.

  - 이 문제의 극단적인 형태가 **검증문 없는 테스트(assertion-free testing)** 입니다.

```swift
func test_meaningless() {
  _ = isStringLong("abc")
  _ = isStringLong("abcdef")
}
```

  - 이 테스트는 코드 커버리지와 분기 커버리지가 모두 100%지만 아무것도 검증하지 않습니다.

* **어떤 커버리지 지표도 외부 라이브러리의 코드 경로를 계산에 넣지 못합니다.**

```swift
func parse(_ input: String) -> Int {
  return Int(input) ?? 0
}
```

  - 테스트 하나로 100% 커버리지가 나옵니다.
  - 그러나 `Int(_:)` 가 내부에서 처리하는 수많은 입력(빈 문자열, 공백, 부호, 오버플로 등)은 전혀 검증되지 않았습니다.

##### 1.3.4 특정 커버리지 수치를 목표로 삼기

* 수치가 낮다면(예: 10%) 테스트가 부족하다는 **좋은 신호** 입니다.
* 그러나 100%라고 해서 좋은 테스트 스위트라는 보장은 전혀 없습니다.
* 특정 수치를 조직 차원의 목표로 강제하면 해롭습니다.
  - 개발자는 지표를 채우기 위해 검증 없는 테스트를 양산하게 됩니다.

> TIP: 커버리지는 참고용 신호로만 쓰고, 반드시 통과해야 하는 관문으로 삼지 마십시오.

### 1.4 성공적인 테스트 스위트의 특징

* 테스트 스위트의 품질을 재는 유일한 신뢰할 만한 방법은 **테스트를 하나씩 개별적으로 평가하는 것** 입니다.
* 자동화된 방법은 없습니다. 개인의 판단을 적용해야 합니다.
* 물론 한 번에 전부 평가할 필요는 없고, 점진적으로 해나가면 됩니다.

##### 1.4.1 개발 주기에 통합되어 있다

* 자동화된 테스트를 두는 유일한 이유는 그것을 **끊임없이 사용** 하기 위해서입니다.
* 이상적으로는 아무리 작은 변경이라도 코드가 바뀔 때마다 실행되어야 합니다.

##### 1.4.2 코드베이스에서 가장 중요한 부분만 표적으로 삼는다

* 모든 테스트가 동등하지 않듯, 코드베이스의 모든 부분이 같은 관심을 받을 가치가 있는 것도 아닙니다.
* 테스트의 가치는 테스트 자체의 구조뿐 아니라 **무엇을 검증하는가** 에서도 나옵니다.
* 대부분의 애플리케이션에서 가장 중요한 부분은 비즈니스 로직, 즉 **도메인 모델** 입니다.
  - 여기에 투자하는 것이 시간 대비 최고의 수익을 냅니다.

* 나머지는 세 가지로 나뉩니다.
  - 인프라 코드
  - 데이터베이스나 서드파티 시스템 같은 외부 서비스와 의존성
  - 모든 것을 하나로 이어 붙이는 코드

* 인프라 코드에 복잡하고 중요한 알고리즘이 있다면 그쪽도 충실히 테스트하는 것이 맞습니다.
* 다만 대부분의 관심은 도메인 모델에 가야 합니다.
* 이 지침을 따르려면 먼저 **도메인 모델을 나머지 관심사로부터 분리** 해 두어야 합니다.

##### 1.4.3 최소한의 유지 비용으로 최대의 가치를 낸다

* 단위 테스트에서 가장 어려운 부분이며, 이 책 전체의 주제이기도 합니다.
* 빌드 시스템에 테스트를 넣는 것만으로도, 도메인 모델의 커버리지를 높게 유지하는 것만으로도 충분하지 않습니다.
* **가치가 유지 비용을 충분히 넘어서는 테스트만** 스위트에 남겨야 합니다.

* 이 능력은 둘로 나뉩니다.
  - 가치 있는 테스트를 **알아보는** 능력 — 판단의 기준틀이 필요합니다.
  - 가치 있는 테스트를 **작성하는** 능력 — 설계 능력이 필요합니다.

### 1.5 이 책에서 배우는 것

* 앞으로 좋은 테스트와 나쁜 테스트를 구분하는 기준틀을 세우고, 그 기준으로 기존 테스트를 분석하고 리팩토링하는 법을 다룹니다.
* 좋은 테스트를 알아보는 기준은 <doc:Chapter-4>에서 네 가지 속성으로 정리됩니다.
* 그에 앞서 <doc:Chapter-2>에서 '단위 테스트'라는 말의 정의부터 정리합니다.
