# 2. 단위 테스트란 무엇인가?

## 요약

'단위 테스트'라는 말이 사람마다 다르게 쓰이는 이유를 짚고, 고전파와 런던파라는 두 학파의 차이를 비교합니다.

### 2.1 '단위 테스트'의 정의

단위 테스트에는 세 가지 중요한 속성이 있습니다.

* **작은 코드 조각(단위)** 을 검증한다
* **빠르게** 수행한다
* **격리된** 방식으로 처리한다

앞의 두 가지는 논쟁의 여지가 거의 없습니다. 문제는 세 번째, **격리** 를 무엇으로 볼 것인가입니다.

이 지점에서 학파가 갈립니다.

> 정의: **테스트 더블(test double)** 은 실제 의존성처럼 보이고 동작하지만 실제로는 단순화된 가짜 객체입니다.

##### 2.1.1 격리 문제: 런던파의 관점

* **테스트 대상 시스템(SUT)을 협력자로부터 격리** 하는 것으로 봅니다.
* 클래스가 다른 클래스에 의존하면, 그 의존성을 테스트 더블로 대체합니다.

```swift
protocol Store {
  func hasEnoughInventory(product: Product, quantity: Int) -> Bool
  func removeInventory(product: Product, quantity: Int)
}

final class Customer {
  func purchase(store: Store, product: Product, quantity: Int) -> Bool {
    guard store.hasEnoughInventory(product: product, quantity: quantity) else {
      return false
    }
    store.removeInventory(product: product, quantity: quantity)
    return true
  }
}
```

런던파 스타일의 테스트입니다.

```swift
final class StoreMock: Store {
  var hasEnoughInventoryResult = false
  private(set) var removeInventoryCalls: [(Product, Int)] = []

  func hasEnoughInventory(product: Product, quantity: Int) -> Bool {
    return hasEnoughInventoryResult
  }

  func removeInventory(product: Product, quantity: Int) {
    removeInventoryCalls.append((product, quantity))
  }
}

func test_purchase_fails_when_not_enough_inventory() {
  // 준비
  let storeMock = StoreMock()
  storeMock.hasEnoughInventoryResult = false
  let sut = Customer()

  // 실행
  let success = sut.purchase(store: storeMock, product: .shampoo, quantity: 5)

  // 검증
  XCTAssertFalse(success)
  XCTAssertTrue(storeMock.removeInventoryCalls.isEmpty)
}
```

* `Store`의 실제 구현은 전혀 관여하지 않습니다.
* 이 테스트가 실패하면 문제가 `Customer` 안에 있다는 것이 확실합니다.

> 정의: **테스트 대상 메서드(MUT)** 는 테스트가 호출하는 SUT의 메서드입니다.

> 정의: **목(mock)** 은 SUT와 협력자 사이의 **상호작용을 검사** 할 수 있게 해주는 특별한 종류의 테스트 더블입니다.

##### 2.1.2 격리 문제: 고전파의 관점

* **테스트끼리 서로 격리** 하는 것으로 봅니다.
* 테스트가 서로 영향을 주지 않고 어떤 순서로든, 병렬로도 실행될 수 있어야 한다는 뜻입니다.
* 이를 위해 대체해야 하는 것은 협력자 전부가 아니라 **공유 의존성** 뿐입니다.

같은 코드를 고전파 스타일로 테스트하면 다음과 같습니다.

```swift
func test_purchase_succeeds_when_enough_inventory() {
  // 준비 - 실제 구현을 그대로 사용
  let store = InMemoryStore()
  store.addInventory(product: .shampoo, quantity: 10)
  let sut = Customer()

  // 실행
  let success = sut.purchase(store: store, product: .shampoo, quantity: 5)

  // 검증 - 호출 기록이 아니라 최종 상태를 확인
  XCTAssertTrue(success)
  XCTAssertEqual(5, store.getInventory(product: .shampoo))
}
```

* 고전파에서 '단위'는 반드시 한 클래스일 필요가 없습니다. **여러 클래스의 묶음** 이어도 됩니다.
* 다만 그 묶음 중 어느 것도 공유 의존성이어서는 안 됩니다.

### 2.2 고전파와 런던파

두 학파가 갈리는 뿌리는 **격리** 속성입니다. 여기서 파생된 이견은 세 가지 주제로 뻗어 나갑니다.

* 격리 요구사항
* 무엇을 테스트 대상 코드(단위)로 볼 것인가
* 의존성을 어떻게 다룰 것인가

| | 격리 대상 | 단위란 | 테스트 더블 사용 대상 |
|:--|:--|:--|:--|
| 런던파 | 단위 | 클래스 하나 | 불변 의존성을 제외한 모든 것 |
| 고전파 | 단위 테스트 | 클래스 하나 또는 여러 개 | 공유 의존성 |

##### 2.2.1 두 학파가 의존성을 다루는 방식

* 런던파도 모든 의존성을 대체하지는 않습니다. 판단 기준은 **가변인가** 입니다.
* 절대 변하지 않는 객체, 즉 **불변 객체** 는 대체하지 않아도 됩니다.
  - 앞선 런던파 예시에서도 `Product`는 목으로 바꾸지 않고 실제 값을 그대로 썼습니다.
  - `quantity` 로 넘긴 숫자 `5`도 마찬가지입니다. 이 숫자를 목으로 만들 이유는 없습니다.

> 정의: **값 객체(value object)** 는 개별적인 정체성이 없고 오직 내용으로만 식별되는 불변 객체입니다.
>
> 내용이 같으면 어느 인스턴스를 쓰든 차이가 없으므로 서로 교체할 수 있습니다.

의존성의 계층은 다음과 같습니다.

```
의존성
├─ 공유 의존성 ................ 고전파가 대체하는 대상
└─ 비공개 의존성
   ├─ 가변 ..................... 런던파가 추가로 대체하는 대상
   └─ 불변 (값 객체) ........... 어느 쪽도 대체하지 않음
```

* 데이터베이스는 **공유 의존성** 입니다. 내부 상태가 모든 테스트에 걸쳐 공유되기 때문입니다.
* `Store` 인스턴스는 **가변인 비공개 의존성** 입니다.
* `Product`나 숫자 `5`는 **불변인 비공개 의존성**, 곧 값 객체입니다.
* 모든 공유 의존성은 가변이지만, 가변 의존성이 공유가 되려면 테스트들이 그것을 재사용해야 합니다.

> **협력자(collaborator)** 는 공유이거나 가변인 의존성입니다.
>
> `sut.purchase(store: store, product: .shampoo, quantity: 5)` 에는 의존성이 셋 있지만,
> 협력자는 `store` 하나뿐입니다. 나머지 둘은 값 객체입니다.

* **공유 의존성과 프로세스 외부 의존성은 같은 말이 아닙니다.**
  - 공유 의존성은 거의 항상 프로세스 밖에 있지만, 그 역은 성립하지 않습니다.
  - 프로세스 외부 의존성이 공유가 되려면, 테스트들이 그것을 통해 서로 소통할 수단이 있어야 합니다.
  - 예를 들어 상품 목록만 돌려주는 **읽기 전용 API** 는 프로세스 밖에 있지만 공유 의존성이 아닙니다. 테스트가 그 데이터를 바꿀 수 없으므로 서로 간섭할 수 없기 때문입니다.
  - 반대로 싱글턴이나 정적 필드는 프로세스 안에 있지만 공유 의존성입니다.

* 다만 실무에서는 프로세스 외부가 아닌 공유 의존성을 만나는 일이 드물기 때문에, 이 책은 두 용어를 대체로 같은 뜻으로 씁니다.

### 2.3 고전파와 런던파 비교

##### 2.3.1 한 번에 한 클래스 테스트하기

* 런던파는 '단위'를 **클래스** 로 봅니다.
* 그러나 클래스는 단위의 자연스러운 경계가 아닙니다.
* 테스트가 검증해야 하는 것은 클래스가 아니라 **동작의 단위(a unit of behavior)** 입니다.
  - 하나의 동작이 여러 클래스에 걸쳐 있을 수 있습니다.
  - 반대로 한 클래스가 여러 동작을 담고 있을 수도 있습니다.
* 클래스 단위로 테스트를 강제하면 테스트가 구현 세부 사항에 결합됩니다.

##### 2.3.2 상호 연결된 클래스의 큰 그래프 테스트하기

* 런던파는 목을 쓰면 거대한 의존성 그래프를 준비하지 않아도 된다고 주장합니다.
* 그러나 저자는 이를 문제의 **해결이 아니라 은폐** 로 봅니다.
* 클래스 그래프가 지나치게 크다는 것은 그 자체로 **설계 결함의 신호** 입니다.
* 목으로 가릴 것이 아니라 설계를 고쳐야 합니다.

##### 2.3.3 정확한 버그 위치 찾기

* 런던파에서는 실패하는 테스트가 하나뿐이므로 버그 위치를 바로 알 수 있습니다.
* 고전파에서는 하위 클래스의 버그 하나가 그 클래스를 쓰는 모든 테스트를 함께 깨뜨립니다.
* 이는 런던파의 실질적인 장점이지만, 그리 큰 문제는 아닙니다.
  - 전체 테스트 스위트를 정기적으로 실행한다면, 실패 지점 중 가장 아래쪽 테스트를 보면 됩니다.
  - 오히려 함께 깨진 테스트들이 그 버그의 파급 범위를 알려줍니다.

##### 2.3.4 그 밖의 차이점

* **TDD 진행 방향**
  - 런던파: 상위 수준 테스트부터 시작해 아래로 내려가는 **아웃사이드 인(outside-in)**
  - 고전파: 도메인 모델부터 시작해 위로 올라가는 **인사이드 아웃(inside-out)**

* **과도한 명세**
  - 런던파는 목으로 상호작용을 검증하므로 구현 세부 사항을 명세에 끌어들이기 쉽습니다.
  - 이것이 테스트 취약성의 주된 원인이며, <doc:Chapter-5>에서 자세히 다룹니다.

> 저자는 **고전파** 를 선호하며, 이 책은 고전파의 정의를 따릅니다.

### 2.4 두 학파의 통합 테스트

* 런던파는 실제 협력자 객체를 쓰는 테스트를 모두 통합 테스트로 봅니다.
  - 고전파 스타일로 쓴 테스트 대부분이 런던파에게는 통합 테스트입니다.

* 고전파의 관점에서 단위 테스트를 다시 정의하면 다음과 같습니다.

> 정의: **단위 테스트** 는 다음 세 가지를 **모두** 만족하는 테스트입니다.
>
> 1. 단일 **동작 단위** 를 검증한다
> 2. 빠르게 수행한다
> 3. 다른 테스트와 격리되어 처리된다
>
> 이 중 하나라도 만족하지 못하면 **통합 테스트** 입니다.

* 공유 의존성(예: 데이터베이스)에 접근하는 테스트는 다른 테스트와 격리되어 실행될 수 없습니다.
  - 한 테스트가 바꾼 데이터베이스 상태가 같은 데이터베이스를 쓰는 다른 테스트의 결과를 바꿉니다.
  - 이를 피하려면 테스트를 순차적으로 실행해야 합니다.

* 프로세스 외부 의존성에 접근하면 테스트가 느려집니다.
  - 데이터베이스 호출 한 번에 수백 밀리초가 더해집니다.
  - 처음에는 대수롭지 않아 보여도, 스위트가 커지면 1초가 아쉬워집니다.

* 두 개 이상의 동작 단위를 검증하는 테스트도 통합 테스트입니다.
  - 다만 이 경우는 대개 이미 느린 테스트를 합친 결과라서, 판단의 결정적 기준이 되지는 않습니다.

##### 2.4.1 종단 간 테스트는 통합 테스트의 부분 집합

* 통합 테스트는 코드가 공유 의존성, 프로세스 외부 의존성, 혹은 다른 팀이 개발한 코드와 잘 맞물려 동작하는지 검증합니다.
* **종단 간(end-to-end) 테스트** 는 그 부분 집합입니다.
* 차이는 포함하는 의존성의 개수입니다.
  - 통합 테스트는 보통 프로세스 외부 의존성 하나만 다룹니다.
  - 종단 간 테스트는 전부 또는 대부분을 실제로 사용합니다.
* 경계가 흐릿할 때도 있지만, 종단 간 테스트는 가장 높은 확신을 주는 대신 가장 느리고 유지 비용도 큽니다.
